## 2026-09-02 — S5: `bt5 design` as a thin argv adapter, no new package, no CSV-format guess

**Decided:** `bt5/cli.py` lives inside the existing `packages/engine/src/bt5` package
(`CLAUDE.md` section 0: "One package"), with a `bt5.cli:main` entry point registered in
`[project.scripts]` and a `__main__.py` so `python -m bt5` works identically. `bt5 design`
is a single argparse subcommand: it reads a backbone GenBank and a protein (inline or from
a file), calls `bt5.design.design()` with every argument keyword, writes the returned
`SkeletonResult.genbank` to disk, prints `SkeletonResult.rendered` plus `.notes` to stdout
(or nothing, under `--quiet`), and optionally writes a plain `Name,Sequence` order CSV via
`bt5.score.order.write_csv` + `entry_name` over the winning candidate's `cds`. `table_id`,
`modality` and `--host` are all required flags with no default, mirroring `design()`'s own
refusal to default `table_id` (`CLAUDE.md` section 3.1).

**No `[tool.mypy] files` or hatch `packages` change.** Both already read
`["packages/engine/src/bt5"]`, and `cli.py`/`__main__.py` sit inside that path, so they
were typechecked and packaged for free. The buildout brief flagged this as one of two
decisions needing `/architect` because it assumed a new top-level package; putting the CLI
inside the existing package instead means there is no cross-lane CI surface to extend, and
therefore nothing to run `/architect` on. The `pyproject.toml` diff this session is exactly
`[project.scripts] bt5 = "bt5.cli:main"`, in its own commit.

**Order file is a plain CSV, not the IDT `.xlsx` plate.** `bt5.score.order` exports two
writers: `write_idt_plate` (a real `openpyxl` workbook, one vendor's specific upload
template, requires the `export` extra) and `write_csv` (`Name,Sequence`, no extra needed).
`docs/PLAN.md:490-495`'s target phrase is "order CSV", and the CLI's `--out-order` flag
writes literally that — no vendor-specific formatting decision embedded in the general-
purpose CLI. A user who wants an IDT plate workbook already has `bt5.score.order` importable
from Python; the CLI does not need to choose their vendor for them.

**No new field read off `SkeletonResult` beyond what exists today.** There is no gallery,
no order entries, and no percentiles on `SkeletonResult` yet (`design/runner.py:75-86`) —
S1 is adding those in parallel and has agreed only to add fields, never rename or remove
one. The CLI builds its own single `OrderEntry` from `result.result.candidates[0].cds` and
`.design_hash` rather than waiting on or guessing at S1's shape. When S1 lands a real order
CSV / gallery on `SkeletonResult`, `--out-order` becomes a place to switch to reading it
directly — a follow-up, not a blocker for this PR.

**`--protein-file` accepts a bare sequence or single-record FASTA**, stripping any line
starting with `>` and joining the rest. `design()` itself only takes a `str`; the CLI does
not use Biopython's FASTA parser here because the surface is one optional `>` header line,
not multi-record files, and pulling in `Bio.SeqIO` for that would be the CLI silently
picking the first record of a file that might hold more than one protein.

**Rejected:**
- *A separate top-level `packages/cli/` (or similar) package outside `bt5`.* Would require
  extending `[tool.mypy] files` and the hatch wheel `packages` list — a CI-wide, cross-lane
  change per the buildout's own mutex rules, solely to hold one module that has no reason
  to live outside the existing package. `CLAUDE.md` section 0 is explicit that this project
  is one package.
- *A third-party CLI framework (`click`, `typer`).* Neither is declared in `pyproject.toml`,
  and `CLAUDE.md` section 5 / the buildout's `pyproject.toml` mutex make "no new dependency"
  a hard rule for this session specifically. `argparse` (stdlib) covers one subcommand with
  required/choice validation without needing one.
- *Defaulting `--table-id`, `--modality`, or `--host` to something "sensible".* `design()`
  refuses to default `table_id` because a wrong genetic code table is a silently wrong
  protein (`CLAUDE.md` 3.1); a CLI-level default would reintroduce exactly the mistake the
  function signature was built to prevent, one flag away.
- *Rendering `BiosecurityVerdict` status directly in the CLI.* The status lives inside
  `DesignContext`, which `SkeletonResult` does not expose; the walking skeleton's own
  `_degradations()` already turns `"not_run"` into the human-readable note "protein-level
  biosecurity screening did not run", which the CLI prints verbatim via `.notes`. Reading
  the raw enum from a private path just to reformat a sentence that already exists would be
  the CLI inventing a second source of truth for the same fact.
- *A `packaging/install.sh` script.* PLAN.md's G8 acceptance bar is "clean install works",
  not "a bespoke script exists" — the real command is two `uv` invocations already
  documented in the root `README.md`'s Development section. A script would either
  duplicate that or drift from it. `packaging/README.md` documents the flow and the
  `commec` two-tier database story instead, and says plainly that biosecurity screening is
  not wired into `design()` yet (that is S2/M2's lane), rather than implying a `--screen`
  flag exists when it does not.

**Where:** branch `claude/s5-cli-packaging`.
